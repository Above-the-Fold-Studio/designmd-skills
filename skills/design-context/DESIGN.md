# Design Context

## Outcome

A shared brief that lets people and agents make coherent interface decisions
without rediscovering the product on every task.

## Use it when

- Starting a new product surface or significant redesign.
- Different pages feel as if they came from different products.
- Requirements name visual adjectives but not their implications.
- An agent has code access but lacks audience, brand, or outcome context.

## Do not use it when

Use interface-critique for a bounded review of an existing interface. Use a
specialized foundation skill when the context is settled and the task is
specifically typography, color, layout, hierarchy, or accessibility.

## Good context is evidence-sized

The brief should be proportional to the decision. A settings panel may need a
paragraph; a product redesign may need a durable document. Unknowns remain
labeled instead of becoming invented facts.

Useful context explains consequences. "Calm" may imply fewer competing accents,
slower motion, lower density, and direct language. "Operational" may imply
compact scanning, persistent state, and stronger status differentiation. These
are hypotheses to validate, not automatic rules.

## Example request

> Read this product area and give me the design context we should preserve
> before redesigning onboarding.

## Optional DesignMD enhancement

DesignMD may supply private design-system context when authorized. The
standalone workflow works from local artifacts and user-provided evidence.
